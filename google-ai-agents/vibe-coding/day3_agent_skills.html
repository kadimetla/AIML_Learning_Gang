Introduction

What Are Agent Skills? The 4 Friction Points They Solve

An Agent Skill is a folder containing a SKILL.md file with optional scripts/, references/, and assets/ directories. By early 2026, public skill marketplaces crossed 40,000+ listings with tens of thousands published in January alone. Why the explosion?

Problem 1 · Context Rot

Too Many Instructions = Worse Results

Dumping every instruction into a single system prompt inevitably degrades LLM performance — a problem known as context rot. Researchers at Chroma (2025) found that across 18 frontier models (Claude 4, Gemini 2.5, Qwen3), performance degrades as input grows, even when task difficulty is held constant.

Skills solve this by loading exclusively on demand. Metadata always. Body only when triggered. Resources only when needed. An agent with 50 skills pays the token cost of only the one it's currently using.

Anthropic published examples where converting workflows to skills cut active context from ~150,000 tokens to ~2,000 — a 98%+ reduction.
Problem 2 · No Procedural Memory

LLMs Know What & When, But Not How

LLMs have episodic memory (what happened) and semantic memory (facts). What they've lacked is procedural memory — how to execute tasks step by step.

Agent Skills are the first credible procedural memory primitive for LLM agents. They encode the "how" in a versioned, testable, retrievable form. The agent never starts from scratch on a workflow it's done before.

Problem 3 · Multi-Agent Overload

Skills Simplify Architectures

The ecosystem was flooded with complex multi-agent systems notoriously hard to build and maintain. Skills allow a single general-purpose agent to seamlessly flex into many specialist roles — without separate agents for each domain.

Instead of a router dispatching to a fleet of sub-agents, you have one agent with a library of skills. Skills can run commands, call MCP servers, and bundle Python scripts. You maintain skills, not agents. The operational surface shrinks dramatically.

Important: Skills do NOT kill multi-agent architectures. Multi-agent remains correct when you have genuine parallelism, capability boundaries, adversarial setups, or heterogeneous models. Skills fill the missing primitive for the middle ground.
Problem 4 · Portability Gap

A Folder is Perfectly Portable

A folder with a markdown file is a remarkably lightweight primitive. Any agent with filesystem access can use them — perfectly portable across a multi-vendor AI landscape.

Claude Code, Gemini CLI, Antigravity, Cursor, GitHub Copilot, Codex CLI — they all support the same Skills standard (agentskills.io). Build once, run anywhere.

Anatomy

Skill Anatomy: SKILL.md + Progressive Disclosure

Canonical Structure (agentskills.io open standard)
cafe-preparation/ ├── SKILL.md # REQUIRED: metadata + instructions ├── scripts/ │ ├── calc_quantities.py # Optional: executable code (any lang) │ └── convert_to_ingredients.py ├── references/ │ ├── menu_and_recipes.md # Optional: supplementary context │ └── minimums.md # Loaded on demand — not always └── assets/ ├── prep_sheet_template.md # Optional: templates, schemas └── shopping_list_template.md
Progressive Disclosure: 3 Load Levels
LEVEL 1 — Always Loaded (~50 tokens)

Metadata only: name + description field. Agent knows the skill exists. Sees when to use it. Pays minimal token cost. An agent with 100 skills carries only ~5,000 tokens of always-loaded metadata.

LEVEL 2 — On Trigger (~2,000 tokens)

Full SKILL.md body loaded when the trigger phrase/task type matches. The agent gets complete procedural instructions for this specific workflow.

LEVEL 3 — On Demand (scripts never pollute context)

Reference docs fetched only when body references them. Scripts execute without ever polluting the token window — they run externally and return results.

Minimal SKILL.md Template
--- name: cafe-preparation description: | Calculates daily ingredient needs and generates prep sheets for cafe operations. Use when the user asks to estimate daily quantities, convert drinks to ingredients, or generate shopping lists. Do NOT use for employee shift scheduling or accounting. version: 1.0.0 license: MIT allowed-tools: [Read, Bash, Write] metadata: author: your-handle --- # Skill Name ## When to use - [Concrete scenario with trigger keywords] - [Another concrete scenario] ## When NOT to use - [Out-of-scope scenario] ## Workflow 1. [Step 1] 2. [Step 2] 3. See `references/advanced.md` for [edge case] ## Examples - Input: "..." → Output: "..." ## Anti-patterns to avoid - Don't [...]
The description field is your routing algorithm. It's the only thing the model sees to decide whether to load the skill. State what it does, front-load trigger keywords, include "Do NOT use for" clauses, be explicit. Spend more time here than anywhere else.
Building Skills

Two Paths to Build a Skill · How to Install

Path A · Subject Matter Expert → Skill

"Translate what you already know"

A compliance officer with a 30-page runbook. An HR manager with onboarding guides. A customer success lead with troubleshooting playbooks. They already have the content.

The job: Translate institutional knowledge into SKILL.md format. No coding required. The result is machine-executable know-how that's also human-readable, versioned, and testable.

1️⃣Interview a domain expert for 1 hour — record it
2️⃣Pick the most repeated workflow from the transcript
3️⃣Draft SKILL.md from transcript. Write 3 eval cases before drafting the body
4️⃣Ship to read-only tier. Test in production-like conditions
5️⃣Iterate description until trigger accuracy clears 90%
Path B · Crystallize a Successful Agent Run

"The agent creates the skill — you review"

If an agent successfully executes a non-trivial, repetitive task, capture that successful trajectory as a Skill. You don't author — you review.

Tools supporting this: Anthropic's skill-creator, Nous Research's Hermes Agent, self-improving-agent-skills pattern. The agent watches a successful trajectory and proposes a SKILL.md draft.

Critical: An un-reviewed agent-drafted Skill is often worse than no Skill at all. The same quality bar applies regardless of author — human or AI.
Three Install Paradigms

1. File Drop (Coding Agents & CLIs)

Drop the skill folder into a specific hidden directory. A convention is emerging around .agents/skills/ at project root. Each tool still has its own path — community managers like skillport or openskills symlink your central library to every tool's expected location.

2. UI Install (Web & Enterprise Workspaces)

Web-based platforms and AI chatbots allow upload/management through a visual registry UI. Handles routing behind the scenes for your whole team — no terminal access needed for non-developers.

3. Programmatic (Custom Frameworks)

If building with Google ADK, load skills programmatically. Point code to the folder path — register via SkillToolset class which auto-generates load_skill routing tools for the model.

# ADK programmatic install
from google.adk.skills import SkillToolset
toolset = SkillToolset(skills_dir="./skills")
Skill vs. MCP vs. AGENTS.md
🔌MCP = Reach. Connects agent to external systems (Drive, BigQuery, Salesforce). Skills use MCP as their tool layer.
🧩Skills = Know-how. Teaches agent HOW to think about a type of work. Procedural memory that calls MCP tools when needed.
📋AGENTS.md = Identity. Always loaded. Project conventions, stack, build commands. Acts as skill router — a short catalog at the bottom tells the agent what skills are available.
Architecture Decision

Why Skills Beat Multi-Agent for Many Use Cases: The Logistics Example

A logistics company with 100 process variants (product type, route constraints, customer SLAs, regulatory zones). Four architectural options — dramatically different outcomes:

Option A: One Giant Context Window

All 100 variants loaded into a single system prompt. Immediate context rot. Exorbitant token costs. LLM performance degrades before you ship the first feature. Eliminated immediately.

Option B: RAG over Runbooks

Probably the right answer 2 years ago. Now you're running a vector DB, embedding model, and chunking strategy whose quality is orthogonal to the actual procedures. High operational overhead for questionable benefit. Outdated pattern.

Option C: Multi-Agent (1 per variant)

100 subagents, each with a process-specific system prompt. Operational nightmare: 100 deployments, 100 evaluation surfaces, complex routing layers. CI/CD for the HR sub-agent accidentally breaks the invoice sub-agent. Too much surface area.

Option D: One Agent + 100 Skills ✓

Progressive disclosure: 100 skills × ~50 tokens = ~5,000 tokens of always-loaded metadata. Logistics requests carry strong activation cues (SKU, origin, weight, hazmat flag, SLA) making skill descriptions sharp and selection reliable. Adding variant #101 = a new folder, not a new deployment. The winner.

The Runtime Insight

98.4% is Infrastructure

A reverse-engineering of Claude Code v2.1.88 found that 98.4% of the codebase is operational infrastructure: permission classifiers, context compaction, subagent delegation, session storage. Only 1.6% is the agent loop itself.

The model sits behind a remote API. The engineering around it — and specifically the skills library — is what makes the system production-grade. Skills are the unit of improvement, not model swaps.

The Strategic Point

Skills = The Durable Asset

Two companies running on the same agent runtime with the same MCP tools will produce different outcomes. Their skills library encodes what they actually know. The runtime is commoditized. A retailer that invests in skills, even on a generic runtime, is building a durable competitive moat.

Evaluating Skills

Evaluation: The 4 Failure Modes & The Golden Rules

An Agent Skill without a test is a hope, not a capability. When researchers benchmarked 84 real-world agent tasks in SkillsBench (2025), they found that 19% of skills performed worse than no skill at all. These failures are predictable.

Failure Mode 1: Trigger Failure

Wrong skill fires / correct one doesn't fire

Vercel's production analysis found a 56% non-invocation rate for skills expected to activate consistently. A skill stripped of instructions scored 58%, while the agent without the skill scored 63% — a 5-point deficit proving poorly designed skills actively subtract capability.

Fix: The description must pass 4 checks — testable specificity (3 positive + 3 negative triggers), clarity (no overlap with adjacent skills), execution fidelity (describes actual not aspirational behavior), and rephrasing stability (routes regardless of phrasing).

Failure Mode 2: Execution Failure

Skill triggers correctly but produces bad output or wrong tool calls

Latitude's analysis (March 2026) found that final-output-only scoring passes 20-40% more cases than trajectory-aware scoring. This gap = agents reaching correct answers via incorrect tool sequences. Acceptable in read-only scenarios. Critical in action-allowed skills where incorrect trajectories cause irreversible side effects.

Failure Mode 3: Token Budget Failure

Skill body crowds context, degrading unrelated turns

Never evaluate a skill in isolation. Agents in production co-load 5-15 skills simultaneously. A skill body exceeding 5,000 tokens might work perfectly alone but causes context rot when co-loaded. MCPVerse found an 18.2% accuracy drop in Claude-4-Sonnet due to tool proliferation.

The "Lost in the Middle" effect applies: relevant information at the start or end performs best — the middle degrades. Long skill bodies put critical instructions in the worst possible position.

Failure Mode 4: Regression

New skill breaks previously working routing

A newly added skill overlaps with an existing one. The description triggers on queries that were correctly handled by a different skill. Old workflows break. This is only detectable when the full library is exercised together — hence the graduation process.

pass^k (run evaluation k times, require success on every run) is the correct metric. On tau-bench, GPT-4o scored 61% on pass^1 but dropped below 25% on pass^8 — single-run success is a poor predictor of production reliability.

Evaluation-Driven Development (EDD)

Write Eval Cases BEFORE Writing the Skill Body

Invert the workflow: write 3 JSON evaluation cases (Input, Expected Tools, Expected Output) before drafting SKILL.md. Forces a clear functional specification upfront. Surfaces description ambiguities and tool-trajectory errors before they compound.

{
  "case_id": "refund_dup_charge_001",
  "input": "I was charged twice for order #4521 last Tuesday",
  "expected_skill": "refund_processor",
  "expected_tool_calls": [
    {"tool": "lookup_order", "args": {"order_id": "4521"}},
    {"tool": "check_duplicate_charge", "args": {"order_id": "4521"}}
  ],
  "expected_output_format": "confirmation_with_refund_id",
  "rubric": ["acknowledges duplicate", "cites order id", "provides next step"]
}
Graduation Tiers

The Read / Draft / Act Ladder

🟢Read-Only: LLM-as-Judge eval; 90% trigger accuracy. Fetches and describes data — cannot mutate state.
🟡Draft-Only: Golden dataset of 20+ cases + human approval. Produces content for human review — cannot send or commit.
🔴Action-Allowed: Full adversarial red-teaming + sustained pass^k success (not just a lucky pass) + no rollback events. May execute irreversible operations on real systems.
Complete Eval Coverage Checklist
☐Trigger: Positive AND negative test cases. Target 90% trigger accuracy.
☐Execution: Correct outputs across a representative range of inputs.
☐Regression: Adding this skill causes zero performance drops in existing library.
☐Token Budget: Co-loaded with 5–15 frequently-active skills, does not degrade unrelated turns.

Failure on ANY single condition holds the skill at draft tier, regardless of happy-path performance.

Trajectory scoring modes (Google ADK):
EXACT → action-allowed skills (critical operations)
IN_ORDER → most action-allowed skills
ANY_ORDER → read-only skills (tolerates ordering variance)
Production Reality

Context Overflow: The Failure Mode That Breaks Demos

The Demo-to-Deploy Gap

What Breaks Perfectly Good Demos in Production

Works in demo: 3 tools, single turn, short history. Fails in production: 15 tools, multi-turn session, conversation history growing with every turn.

Lost in the Middle (Liu et al., TACL 2024): Performance is highest when relevant information sits at the start or end of input — degrades in the middle. A U-curve that holds even for models trained on long contexts.

Context Rot (Chroma Research, 2025): Across 18 frontier models (Claude 4, Gemini 2.5, Qwen3), performance degrades as input grows — even when task difficulty is held constant. Every model gets worse, faster when relevant content is hard to distinguish from distractors.

Why Progressive Disclosure Matters at Scale

Consider an agent with 50 distinct workflows:

Anthropic published examples where converting to skills cut active context from ~150,000 tokens to ~2,000 — a 98%+ reduction. Forty-nine skill bodies sit on disk. Only the active one is in context.

Key Principle 1

Capacity ≠ the right metric

A 1M-token context window can show significant performance degradation at 50K tokens. Window size is not the relevant constraint — what matters is how much noise surrounds the signal.

Key Principle 2

Active context is a budget, not a vessel

Every token in front of the model takes attention from every other token. Treat the system prompt the way infrastructure teams treat memory: a finite resource, allocated deliberately. Skills are memory management for LLMs.

Key Principle 3

Skills resolve the constraint

They keep active context small while keeping available capability effectively unbounded. An agent with 100 skills and a 50K active context is more capable than one with 100K of everything always loaded.

Advanced

Meta-Skills: Skills That Improve Other Skills

Once you have a working skills library, the natural question: can the agent help write, evaluate, and improve skills too? This is meta-skills territory.

4 Buckets of Meta-Skills
1.Authoring: Skills that take a workflow description and produce a draft SKILL.md. Google ADK's "skill factory" pattern. Anthropic's skill-creator walks you through creation, evaluation, and tuning.
2.Trace-based harvesting: Instead of asking humans to describe a workflow, watch the agent do it successfully a few times, then turn that trace into a skill. Human's job shifts to confirming the harvested version captures the right steps — not authoring.
3.Improvement: Skills that take an existing skill + failing eval cases and propose edits. Saboo's SkillOptimizer and Anthropic's description-optimization loop. Karpathy's autoresearch pattern: propose change → run bounded experiment → keep only if metric improves.
4.Library evolution: Skills that grow the library over time (like Voyager's Minecraft skill library). Agent finishes a task it had no skill for, notices it solved a recurring problem, proposes adding a new skill to cover it.
The pattern settling: humans write the first version of every skill. Meta-skills handle repetitive maintenance (tuning descriptions, adding test cases, surfacing regressions). A small subset experiments with full self-extension. This is where things go wrong fastest if eval gates aren't tight.
Where Meta-Skills Fall Apart

Meta-skills only work if your eval suite is good

An agent allowed to edit its own skills will happily optimize for whatever metric you point it at — including metrics that are easy to game.

Without solid trigger accuracy tests, regression tests, and human spot-checks, an autonomous improvement loop will quietly make your library worse while reporting it's getting better.

Safety Rules for Meta-Skills
🛡Always enter at draft tier: Anything an agent writes enters the library at draft tier, regardless of how confident the meta-skill is. Graduates through the same Read/Draft/Act ladder as human-written skills.
👀Human in the loop for first edits: Even when the metric clearly improves, scan the diff. Agents make characteristic mistakes: overfitting descriptions to a few test cases, breaking downstream skills they didn't know existed.
🐢Don't start with meta-skills: Get manual authoring working first. The fastest way to get a bad library is to point an agent at an empty folder and ask it to generate 50 skills.
🚫No auto-deploy without staging gate: Auto-updating skills in production without a staging gate is dangerous. Even if metrics improve, human review before library commits is non-negotiable.
Advanced Composition

Composing Skills: DAG Orchestration + Capability Profiles

DAG Orchestration

Why Linear Pipelines Fail at Scale

Passing raw LLM outputs between isolated skills in a monolithic system is ineffective: state gets obfuscated, execution is non-deterministic, and debugging is hard.

The industry solution is Directed Acyclic Graph (DAG) orchestration:

▸Decoupled State: State routing doesn't rely on accumulating execution history in the LLM's prompt. The DAG controller orchestrates handoffs via structured schema references — not growing conversation history.
▸File Message Bus: Passes structured schema references between subagent nodes. The payload stays out of the model's text input — preventing context bloat.
▸Protected Attention: Abstracting payload from model input preserves the model's capacity for actual reasoning, not state tracking.
Canonical Skill Taxonomy for DAG Nodes
🏗️Generator: Convert user intent into structured artifacts
🛡️Reviewer & Gate: Deterministic gates blocking execution if validation fails
🔄Pipeline: Orchestrate linear paths within the broader DAG
🔍Inversion & Recovery: Force agent to clarify assumptions before execution
📖Domain Context Wrappers: Reference nodes teaching domain conventions
Capability Profiles

Swappable Skill Bundles for Role Switching

Activating every skill degrades routing and overwhelms context. Capability Profiles are specialized personas tailored to specific execution states — modular tool bundles defining:

▸Active skills and tool access for this specific role
▸System instructions and operational guardrails
▸Automated workflows and subagent topologies
▸LLM parameters (model choice, temperature)

During execution, orchestration layer unloads previous system instructions and flushes stale variables before swapping the new Capability Profile into memory. This strict teardown and rebuild prevents context loss.

Context Debt & Shifting Intelligence Left

Don't Hope. Enforce.

When authors attempt deterministic behavior at runtime by bloating skill descriptions ("ALWAYS DO X" in caps), they accumulate Context Debt. Models learn to ignore these imperatives — exactly as humans ignore walls of unreadable warning text.

Shift Intelligence Left: Instead of hoping an LLM correctly interprets complex rules at runtime, distill subjective judgments into deterministic scripts. Push logic out of the LLM's prompt and into testable code. Replace rules with software.

Skill Ecosystem

Selecting Skills from 40,000+ Listings · Trust Tiers

By early 2026, public skill marketplaces crossed 40,000 listings. Google launched the official skills repository at github.com/google/skills. Anthropic, Microsoft, Stripe, and others publish first-party skills. The selection problem is real.

Rule 1: First-Party Skills First

Trust by default — pin a version

For vendor-specific tools: Google's BigQuery skill, the official Stripe skill, anything by the people who built the underlying system. They'll be more correct and more maintained than community alternatives. google/skills, anthropics/skills, stripe/ai, microsoft/skills.

Rule 2: Pin Everything

An unpinned dependency that worked yesterday can fail tomorrow

Community skills evolve. Pin to specific versions like any other dependency. An unpinned skill is a dependency that could silently change its behavior between your test run and your production run.

Rule 3: Audit Before Adopting

A skill is code that runs in your context

Treat it like any other dependency: same supply-chain hygiene. Community skills from individual GitHub repos carry varying maintenance commitment. A skill with a malicious scripts/ file executes in your environment. Inspect before installing.

Case Study

Retail Case Study: Domain Expertise as Code

A home-improvement retailer. The same agent runtime as every competitor. The same MCP tools. The skills library is what differentiates them — encoding what the company actually knows about serving customers.

Illustrative Skills Library
🏗️project-guidance (Read-only · Trades knowledge team)
Turns vague queries ("how do I tile a shower?") into step-by-step plans. Encodes substrate requirements, ordering logic, common-mistake callouts.
📋materials-list (Draft-only · Pro merchandising)
Takes project description → grouped bill-of-materials including items contractors forget. Customer reviews before purchasing.
⭐review-summarize (Read-only · Personalization)
Condenses product reviews into pros, cons, use cases. Triggered when customer asks about real-world experience.
🚚delivery-window (Read-only · Fulfillment)
Computes last-mile options and ETAs given location, store availability, freight network. Updated by the team that manages freight.
↩️return-policy (Read-only · Customer service)
Encodes the dozens of exceptions (special-orders, hazmat, custom cuts). Action-allowed tier (issuing refunds) requires a separate, tighter-reviewed skill.
How the Query Routes

Customer: "I want to remodel my kids' bathroom, what do I need?"

1. Runtime loads L1 descriptions of all skills at session start (~30-80 tokens each, ~2KB total)

2. project-guidance matches → body loads → outlines renovation steps

3. Customer asks about delivery → delivery-window loads

4. Customer asks about returns → return-policy loads

Notice what doesn't happen: no monolithic "remodeling assistant" trained on every scenario. Each piece of expertise loads only when the conversation reaches it. Active context stays small. Available capability: effectively unbounded.

Quick Reference

The Practical Cheatsheet: Do's, Don'ts & The Five Rules

✅ DO
✅Start small and concrete. Run the task yourself first — real failure produces signal, speculation produces noise
✅Spend disproportionate time on the description field — it is the routing algorithm. Include what it does, when to use, and when NOT to use
✅Trust progressive disclosure. Move detail to references/ as the SKILL.md body grows
✅Bundle deterministic work in scripts/, not as instructions — models ignore walls of imperative text
✅Treat Skills as code: version them, pin them, review them in PRs, give them CI tests
✅Skills + MCPs (not vs). Skills teach how to use the tools MCP provides
✅Give the reason, not just the rule. Models generalize to edge cases when they understand WHY an instruction exists
❌ DON'T
❌Write vague descriptions like "helps with documents." Use specific verbs, trigger phrases, and a when-not-to-use clause
❌Write SKILL.md bodies over 5,000 words. Move detail to references/. Over 5K words = two skills
❌Hard-code paths or secrets anywhere in the skill folder
❌Embed "always do X" rules that belong in AGENTS.md (global identity) not in a skill
❌Install untrusted third-party libraries or skills without scanning for supply chain issues
❌Reinvent MCP as scripts — if it's a tool call, it should be an MCP server, not a bash script in scripts/
❌Start with meta-skills before manual authoring works. Don't generate 50 skills on day one.
⚡ THE 5 RULES
R1One skill, one job. If you can't describe it in one sentence, it's two skills. Decompose before writing.
R2Descriptions are an interface. The agent picks skills by reading descriptions. A vague description = an unused skill.
R3Skills are dependencies. Version them, pin them, review in PRs. A skill without a test is a hope, not a capability.
R4The right team owns the right skill. Domain experts own domain skills. AI team must not become a bottleneck for org knowledge.
R5The agent runtime is interchangeable. Don't tie skills to one runtime. Portability is part of the value.
One-Line Mental Model: System prompt = instinct. AGENTS.md = project README. MCP = hands. RAG = library. Skills = the runbook the experienced colleague hands you on day one — that the AI never forgets.
