The Core Shift

"Vibe Coding" ≠ "Vibe In Production": The Paradigm Shift

The Illusion of Speed

Writing Fast ≠ Shipping Fast

An AI coding editor generates 1,000 lines of well-documented code rapidly. It feels like a legion of interns who never sleep. But when a model "hallucinates" — confidently invents something untrue — it doesn't create one bug. It generates 1,000 lines of vibe-consistent but functionally broken logic.

If human reviewers are drowning in a sea of AI-generated PRs, the process isn't faster — it's just creating a bigger pile of "stuff" to be sorted later. The bottleneck has moved downstream to humans who must integrate and review, not those who write.

The Role Shift

Developer → Technical Architect

In traditional engineering, developers spent significant time digging into APIs, debugging line by line, determining if Python uses substring in string or string.includes. Today: coding agents don't just suggest text — they execute tasks.

Most time is now spent writing high-quality specifications — detailed technical instructions telling AI exactly what to build. Code is now disposable. Write a rock-solid spec and the entire codebase can be regenerated. Flip the project from Python to JavaScript in a single afternoon. No emotional attachment to code.

Agentic AI vs. Generative AI

Hybrid Team Member, Not Autocomplete

Standard GenAI: smart autocomplete. Agentic AI: a hybrid team member with tools as hands and an LLM as the brain. It reasons, writes specs and test cases, uses a browser to test UI, commits and merges code in Git.

Give the brain a "vibe" → it guesses. Give it a "blueprint" → it builds. In enterprise software, guessing is how "Rogue Agent" incidents occur. Spec-Driven Development (SDD) prevents this.

The Spec is the Product. The Code is the Output.

— Central thesis of Day 5 whitepaper

What SDD Enables
🔄Regenerate the codebase from scratch if requirements change — no emotional cost
🌐Translate the entire codebase from one language/framework to another in an afternoon
📐AI catches logic flaws in the specification before generating broken code at scale
🧪AI writes more comprehensive test coverage than any human in the same timeframe — because implementation is no longer the bottleneck
The "Context Fragmentation" Problem SDD Solves

Context fragmentation: while a developer is away, a teammate renames a variable in a shared file. An agent quoting an outdated snapshot mints code that calls a function that no longer exists. This is the digital equivalent of the game "Telephone" — the AI starts losing the plot because it's looking at outdated snapshots.

SDD fix: The spec in ./specs/ is the single source of truth — both humans and AI reference it, preventing divergence.

Spec-Driven Development

What Makes a Production-Grade Specification

A good specification is an Architectural North Star — it prevents context fragmentation and serves as the source of truth for both humans and AI. Stored as a Markdown/YAML file in a specs/ folder, checked into version control.

5 Elements of a Production-Grade Spec
1.Full Technical Design: Don't say "make a login page." Address requirements, database schemas (structure of data), and API specifications (contracts for how components communicate). Break it into pieces.
2.Visual Aids: Include diagrams AND a list of specific tools and libraries with exact version numbers. Without version numbers, the agent suggests older versions based on its training cutoff.
3.Background (The "Why"): Give the agent the reason behind the requirement. It will think forward — inferring likely next steps before you ask. Context prevents misinterpretation.
4.BDD Scenarios: What does success look like? What's failure? What are the edge cases? Explicit scenarios using Gherkin eliminate ambiguity completely.
5.Lean formatting: Treat tokenization as a hard physical constraint. Every character, newline, and indentation space translates directly into development budget and system latency.
Pro tip from Lee Boonstra: Write technical designs in Google Docs first. Let architectural plans be read and reviewed by humans. Catch logic flaws in design before AI generates thousands of lines of broken code. File → Download → Markdown into specs/.

Behavior-Driven Development

BDD + Gherkin: Turning Vague Intents into Architectural Blueprints

BDD (Behavior-Driven Development) is the ultimate tool for turning vague human ideas into precise designs that AI can build without guessing. At its core: plain, structured natural language describing exactly how a system should behave, before any code is written. The syntax is Gherkin.

Gherkin: State → Action → Outcome

Forces the LLM to think in structured terms

The Scenario/Given/When/Then template eliminates vague interpretation and keeps the agent on a strict track. Every behavior is precisely specified — no guessing, no filling in blanks.

Scenario
Names the behavior being tested. Sets the context for the reader.
Given
State: What's already true? What context/preconditions exist? What data is in the database?
When
Action: What does the user/system do? The trigger event that initiates the behavior being tested.
Then
Outcome: What should happen? Verifiable, specific, measurable results — not "it should work."
BDD specs serve dual purpose: they're the north star for the AI (what to build) and the test contract for CI (how to verify it). Write the spec → derive failing tests → agent generates passing code. Tests never get deleted because they ARE the spec.
Real BDD Spec Example
Feature: User Authentication Scenario: Successful login with valid credentials Given the user is on the login page at /auth/login And the database contains user "alice@example.com" with hashed password and role: "admin" When the user submits: email: "alice@example.com" password: "correct_password" Then the system returns HTTP 200 with a JWT token And the token payload contains: role: "admin", exp: 3600 And the audit log records: event: "login.success", user_id, timestamp, ip Scenario: Failed login with wrong password Given the user is on the login page When the user submits: email: "alice@example.com" password: "wrong_password" Then the system returns HTTP 401 error: "Invalid credentials" And the audit log records: event: "login.failed" with IP address And no JWT token is issued Scenario: Rate limiting after 5 failed attempts Given the user has failed login 5 times in the last 60 seconds When the user submits another login attempt Then the system returns HTTP 429 error: "Too many attempts, retry after 300s"
Notice: no ambiguity about HTTP status codes, no vague "it should work," specific field names, measurable outcomes. Edge cases (rate limiting) explicitly specified. This is what an AI needs to build exactly what you want.
Instruction Architecture

Where Instructions Live: Three Tiers of Context

Instructions are not written in a single place. Dumping a 100-page system design document directly into a chat window rapidly exhausts the short-term context budget, increases latency, and fragments the context. Each tier has a different scope, lifecycle, and purpose.

1
Chat Interface
Short-lived · Session-specific · Ephemeral · NOT version-controlled
The conversational input box in the IDE (Gemini side-panel, terminal interface). The active developer session only. Use purely for high-level orchestration and instant feedback loops. Example: "Review the design in specs/payment_retry.md and generate the failing unit tests defined in Scenario 3." Don't paste the full spec — reference it by path. Putting specs here exhausts context budget for each new session.
2
Specs Folder
Task-specific · Checked into version control · Source of truth · Persistent across sessions
Static folder directly in the repository (./my-app/specs/my_spec.md). Stores technical design, BDD scenarios, API contracts, structural YAML schemas. The agent dynamically indexes this directory to build and verify code — no manual prompt-stuffing needed. This is the single source of truth for both humans and AI. When the codebase and spec diverge, the AI hallucinates. Agent Skills also live as reusable modules here at .agent/skills/.
3
System Prompts (Hierarchical)
Global + Project · Identity-focused · Engineering DNA · Hierarchical priority
Both Gemini CLI and Google Antigravity scan and concatenate context files hierarchically — each level overrides the one below:
~/.gemini/GEMINI.md
Global profile. Universal persona, default style, core principles. Applies regardless of which project you're in.
./AGENTS.md
Shared cross-tool config. Team-wide foundation. Works across multiple AI clients — prevents instructional fragmentation across Claude Code, Gemini CLI, Cursor, etc.
./.gemini/GEMINI.md
Highest priority. Project DNA. Automatically detected and read by CLI agent. Project-specific rules override everything above.
The priority chain: Project GEMINI.md (highest) → AGENTS.md → Global GEMINI.md (lowest). Skills load on top of whichever system prompt is active, triggered by the description field matching the current task.
Execution Modes

Four Execution Modes: Different Tasks Need Different Mindsets

There isn't just one way to turn a spec into code. Each mode requires a different prompting strategy, different constraints, and a different mental role for the developer-as-architect.

Mode 1: Project Generation (The Architect)

Scaffold from scratch — but never in YOLO mode

Building the skeleton of the project. Key rules:

🚫No YOLO mode: Explicitly prompt the agent NOT to code immediately. It must propose the folder structure and tech stack first for your confirmation
📦Include version numbers for every library. Without them, the agent falls back to its training cutoff — suggesting gemini-1.5-flash because it doesn't know about later versions
🧪Mandate tests, docs, logging from the start. The "digital black box" (logging) is non-optional in production systems
Mode 2: Feature Generation (The Builder)

Implement on top of existing codebase

🎨Match existing style: Prompt the agent to match naming patterns, error handling conventions, and code idioms of the existing codebase — not introduce new ones
👁Confirm multi-file changes: When multiple files are being edited, manually confirm changes before applying. Always see the "Diff" — exactly what lines are being added or removed
🔗Reference the spec by path: "Implement the feature described in specs/feature_xyz.md, Scenario 2 only"
Mode 3: Bug Fixing (The Forensic Specialist)

Root cause analysis — not symptom chasing

🔍Evidence Prompting, not Symptom Prompting:
"Logs pulled via gcloud logging read 'textPayload:ERROR' showed a 403 error" ✓
"The button doesn't work" ✗
🧪Write reproducing test first: Prompt for a failing unit test or curl command before attempting any fix. Keep this test to ensure the bug never returns
🎯Constrain to root cause: Set strict constraint that agent should only fix the root cause. Unrelated "cleanup" complicates the review process
✋Separate renames: If agent suggests renaming variables, treat as a separate task — never bundled with a bug fix
Mode 4: Documentation (The Author)

Docs are the source of truth — keep them in sync

📖Specs in agent skills: Add a skill that automatically maintains README.md and CHANGELOG.md whenever code changes are detected. Documentation drift causes hallucination.
📝Structured docstrings: Use Google Style Docstrings (Python) or JSDoc (TypeScript). These help AI understand what a function does without reading every line of logic — and generate better downstream code that uses these functions
🔄Built-in browser testing (Antigravity): Agent autonomously runs localhost, interacts with live UI, verifies visual fixes in real time — inside an isolated, clean Chrome profile (no access to active sessions)
MCP in Practice

MCP: One Integration, Every Framework

MCP (created by Anthropic, now an open standard) is "the USB-C for AI tools." Build one MCP server for your database (or API, or filesystem), and any MCP-compatible agent can use it without a custom integration. Here's a complete, working implementation in ~40 lines.

mcp_server.py — SQLite database exposed via MCP
import sqlite3
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent

server = Server("knowledge-base")
db = sqlite3.connect("knowledge.db")

@server.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(name="query_knowledge",
             description="Query the knowledge base with SQL",
             inputSchema={
               "type": "object",
               "properties": {"sql": {"type": "string",
               "description": "SQL query (SELECT only)"}},
               "required": ["sql"]
             }),
        Tool(name="add_knowledge",
             description="Add a new knowledge entry",
             inputSchema={"type": "object",
               "properties": {"title": {"type": "string"},
               "content": {"type": "string"},
               "tags": {"type": "string"}},
               "required": ["title", "content"]})
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "query_knowledge":
        sql = arguments["sql"]
        if not sql.strip().upper().startswith("SELECT"):
            return [TextContent(type="text",
                     text="Error: Only SELECT queries allowed")]
        cursor = db.execute(sql)
        rows = cursor.fetchall()
        columns = [desc[0] for desc in cursor.description]
        result = [dict(zip(columns, row)) for row in rows]
        return [TextContent(type="text", text=str(result))]

async def main():
    async with stdio_server() as (read, write):
        init = server.create_initialization_options()
        await server.run(read, write, init)
mcp_client.py — Connect to the server
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

server_params = StdioServerParameters(
    command="python", args=["mcp_server.py"]
)

async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()

        # List available tools
        tools = await session.list_tools()
        print(f"Available: {[t.name for t in tools.tools]}")

        # Call a tool
        result = await session.call_tool(
            "query_knowledge",
            {"sql": "SELECT * FROM knowledge WHERE tags LIKE '%agent%'"}
        )
        print(result.content[0].text)
Why MCP vs Custom REST Wrappers
🔌Build once → every MCP-compatible agent can use it. Claude Code, Gemini CLI, Antigravity, Cursor — same server, zero per-client integration work
🔒Security built in: only SELECT allowed (shown above). Scope enforcement happens at the server, not the prompt
📐Typed schemas via inputSchema: the agent knows exactly what parameters to pass — no hallucinated argument names
🔄Versioned server: update the server once → all clients benefit. No synchronization of multiple custom integrations
Team Culture & Process

Team Culture Evolution: Code Reviews in the AI Age

Sticking to old processes while using modern tools is like trying to put a jet engine on a horse-drawn carriage. AI-generated PRs introduce a new class of team challenges. Here's how to address them.

New Problem 1: Merge Conflicts at Scale

Multiple developers landing on the same file within the hour. PR #1 can't merge without PR #2, which needs PR #3, blocked by a reviewer in a different timezone. Agent-generated code touches more files simultaneously than human-written code.

✅Assign clear file ownership — designate which team members own which APIs vs. UX. Reduce cross-file collisions by design.
New Problem 2: Review Gridlock

A massive PR becomes a Russian-doll of sub-PRs. Human reviewers can't process AI-generated volume at the same pace the agent produces it. Traditional review culture doesn't scale.

✅Bundled AI-generated PR summaries: every PR includes what changed, breakage points, and a risk assessment. Human reviews focus on architecture, not lines.
New Problem 3: Context Fragmentation

Teammate renames a variable in a shared file while another developer is away. An agent quoting an outdated snapshot generates code calling a function that no longer exists. Stale context causes hallucinated integrations.

✅The spec in ./specs/ is the canonical reference. Agents always read spec first, never rely on in-context snapshots of files.
The "Conditional LGTM"

Eliminate 12-hour cross-timezone review delays

A reviewer approves the PR contingent on all automated tests passing. If the tests turn green, the code merges automatically — no second round-trip. Combines human architectural judgment with machine verification of correctness.

Reimagined Ownership

Shift focus of human reviews from nitpicking style on disposable agent-written code → ensuring integrity of architectural blueprints. Style is handled automatically by shared syntax linters or SKILL.md stylebooks. Code is disposable; architecture is not.

Zero-Trust Development

Zero-Trust Development: Building the Safety Net

Real incident: A simple prompt to create a button triggered an unexpected chain reaction. The browser agent autonomously clicked the new button, which was intended for an email agent. Without a specified URL, the agent hallucinated by connecting to a deprecated legacy agent. The result: fifty colleagues received false emails filled with hallucinated content.

— Lee Boonstra, Day 5 whitepaper · context hallucination risk in YOLO mode

This incident highlighted a core risk: when AI lacks sufficient data, it fills gaps using whatever strings exist in its context — including hardcoded email addresses or URLs. Guardrails are not optional.

🛡️
Layer 1: Guardrails (AGENTS.md)
Hard constraints embedded in the agent's system identity. The agent never bypasses these regardless of prompt. Hard-coding constraints into a system prompt alone is brittle — agents can be "convinced" to bypass rules via prompt injection. External, tamper-proof governance is required.
📦
Layer 2: Sandboxing (Ephemeral Containers)
Execute agent-driven tasks within ephemeral, low-privilege containers isolated from primary network and sensitive file systems. If the agent is tricked into executing a destructive command, the damage is confined to a disposable instance. Enable via GEMINI_SANDBOX=docker or Antigravity's Terminal Sandboxing toggle.
🧑‍💼
Layer 3: Human-in-the-Loop (HITL Checkpoint Gates)
High-stakes operations (deploying to production, modifying database schemas, initiating financial transactions) require human confirmation. Present the agent's sanitized intent to a human supervisor for manual sign-off. AI does the heavy lifting; final responsibility for architectural integrity remains in human hands.
🧪
Layer 4: AI-Generated Test Coverage
Force the agent to produce a failing unit test or reproduction command before attempting any fix. Embed automated tests into the codebase — every rapid iteration backed by a verifiable suite. AI can write more comprehensive test coverage than any human in the same timeframe because implementation is no longer the bottleneck.
📊
Layer 5: Evaluation (Behavioral Scoring)
Traditional unit tests ask "did the function return the right value?" — a binary answer. Evaluation asks "is the agent's behavior at least as good as the baseline?" — a scored judgment. Tests catch deterministic regressions; evaluation catches behavioral drift. Essential for any ML-driven component where output is generated, not computed.
🚦
Layer 6: Policy Server (Structural + Semantic Gating)
Intercepts agent actions before they hit external systems. Two layers: (1) Structural — deterministic YAML-based role/environment checks (fast, binary: viewer cannot use send_email). (2) Semantic — a secondary LLM checks if an allowed action is used appropriately (admin can send_email but not with unmasked PII). Creates a safety net separating execution logic from governance logic.
Zero-Trust Implementation

Policy Server + Context Hygiene: Code Walkthrough

policies.yaml — Deterministic Structural Rules
environments:
  localhost:
    blocked_tools:
      - send_email      # Never email from localhost
      - delete_database # Never delete from dev
  production:
    blocked_tools:
      - drop_table      # DDL requires migration

roles:
  viewer:
    allowed_tools:
      - list_files
      - read_file
  editor:
    allowed_tools:
      - list_files
      - read_file
      - write_file
  admin:
    allowed_tools: ["*"]   # All tools, subject to semantic check
policy_server.py — Hybrid Gating (Structural + Semantic)
class PolicyService:
    def is_tool_allowed(self, tool_name: str) -> bool:
        # Check environment blocks first (fast, deterministic)
        env_cfg = self.config["environments"][self.env]
        if tool_name in env_cfg.get("blocked_tools", []):
            return False

        # Check role permissions (fast, deterministic)
        role_allows = (self.config["roles"]
                       .get(self.role, {}).get("allowed_tools", []))
        return "*" in role_allows or tool_name in role_allows

    async def check_action_semantic(self,
                                    action_description: str) -> bool:
        # Secondary LLM checks intent against privacy policy
        prompt = (f"Evaluate if this action violates PII policies: "
                  f"{action_description}")
        response = client.models.generate_content(
            model="gemini-3.1-pro", contents=prompt)
        return not response.text.strip().upper().startswith(
            "VIOLATION")
The 3-Step Execution Flow
1.Structural Check: Is the tool allowed for this role and environment? Check the YAML. Fast, binary, no LLM call needed. Viewer cannot send_email — done.
2.Semantic Check: Are the arguments safe? Ask Gemini if the proposed action violates PII policies. Catches what structural rules can't: an admin allowed to send_email, but not with unmasked email addresses in the body.
3.Execution or Rejection: If both checks pass → tool runs. If either fails → "Policy Violation" returned to agent → agent self-corrects or fails gracefully. No silent failures.
This creates a critical separation of concerns: execution logic and governance logic are separate. The governance layer can be updated without touching application code.
Context Hygiene: resolve_context()

Replaces [[VARIABLE_NAME]] placeholders with runtime values or environment variables. Prevents agents from hallucinating sensitive data (hardcoded emails, API keys, URLs) by keeping templates sanitized.

# In middleware, before every tool call:
resolved_args = {}
for k, v in args.items():
    if isinstance(v, str):
        resolved_args[k] = resolve_context(v)
# [[COMMENTER_EMAIL]] → test_user@example.com
# [[PRESENTATION_ID]] → test-presentation-123

Eliminates the need to hardcode sensitive PII in test suites or system prompts. Any attempt to inject live credentials via template syntax gets sanitized before reaching external systems.
