The Core Framework

Redefining Trust: Two Axes — Security + Evaluation

In deterministic software, trust is binary: code compiles, tests pass, credentials are valid. In agentic systems, an autonomous workforce can execute generated code, access sensitive APIs, and modify production — all without human keystrokes. Trust must be continuously earned.

Axis 1 · Security

Did the agent stay inside the boundary?

Traditional security is deterministic: RBAC, static identity-as-perimeter, binary access tokens. This fails for autonomous agents.

Agentic security requires "Context-as-a-Perimeter" — security enforced based on runtime context because the agent's context IS the attack surface. Every tool call, every intermediate output, every sub-agent handoff is a potential injection point.

⚠️A raw AI model is not an agent. It becomes one when wrapped in a harness — the scaffolding that gives it state, tool execution, feedback loops, and enforceable constraints. Secure the harness, not just the model.
⚠️Effective Trust is a continuous metric evaluated across an agent's supply chain, identity, runtime behavior, and contextual associations — not a gate you pass through once at deployment.
Axis 2 · Evaluation

Was what happened inside the boundary worth shipping?

Security tells you the agent didn't escape its sandbox. Evaluation tells you whether it built the right thing. A vibe-coded agent can pass every security check and still:

▸Fundamentally misread the developer's intent
▸Ignore project conventions and naming patterns
▸Silently degrade user experience
▸Generate code that looks right but is semantically wrong

Three things make vibe coding evaluation uniquely hard: the underspecification gap (no spec exists), the user often can't validate 600 lines of generated code, and the session is iterative with the codebase as live state — bad early decisions compound.

The shift: Traditional RBAC says "does this user have permission?" Agentic ABAC + JIT asks "is this specific action by this specific agent, at this specific moment, with this specific context, appropriate?" Security must be continuously verified at runtime — not granted at deployment and assumed forever.
Security Architecture

The 7-Pillar Agent Security Architecture

A layered defense-in-depth framework. Because the model could fail or be compromised, security cannot reside solely within the AI itself. Must enforce a strict, external "safety envelope" spanning multiple disciplines.

P1
Infrastructure & Networking
Isolate runtime execution in ephemeral, kernel-level sandboxes (gVisor). Strict network egress governance — agent data travels only through authorized, offline caches or explicit internal proxies. Prevents inadvertent public exfiltration.
P2
Data Security
Data at rest: Customer-Managed Encryption Keys (CMEK). Data in transit: mutual TLS (mTLS). Strict least-privilege access scoping. Vector databases must enforce strict tenant partitioning to prevent Cross-Tenant Vector Poisoning.
P3
Model / Prompt Security
System instructions and rule files ARE the new source code. Treat them as highly sensitive, cryptographically attested artifacts. Defend against semantic attacks that subvert model instructions — prompt injection is the new SQL injection.
P4
Application & Runtime
LLM firewalls for dynamic prompt/response filtering. Deterministic "hooks" at lifecycle points (before tool call, after file edit). Centralised Agent Gateways govern A2A orchestration, preventing unauthorized lateral movement.
P5
Identity & Access Management
Unique cryptographic SPIFFE IDs for every agent. ABAC (Attribute-Based) not just RBAC (Role-Based). JIT (Just-In-Time) token downscoping: fresh, hyper-restricted credentials that expire the moment the task concludes. Intent × User × Time permissions matrix.
P6
Observability & SecOps
Without observability, there's no way to tell if an agent is succeeding or quietly drifting. OpenTelemetry traces for all agent.session, agent.think, and agent.tool spans. Autonomous SecOps triad: Red (attack), Blue (monitor), Green (fix).
P7
Governance & Compliance
EU AI Act compliance: Algorithmic Impact Assessments for high-risk autonomous agents. Immutable audit trail attributing every real-world action to a specific agent AND the human who deployed/approved it. "Logic Reviews" replace simple approval buttons.
⊕
Context-as-a-Perimeter
The overarching model replacing Identity-as-a-Perimeter. Security is enforced based on the runtime context of each specific action — not granted statically at deployment. Every layer is defense-in-depth. No single pillar is sufficient alone.
Pillars 1 & 4

Sandboxes, Supply Chain Defence & Application Logic

Ephemeral Sandboxing

Every Execution Starts Clean

The vibe coding loop is inherently iterative: agent writes script → executes → reads error logs → rewrites. This dynamically generated code cannot be implicitly trusted.

Sandboxes must: execute in kernel-level isolation (gVisor), completely block raw host access, and reset state between every run. Not merely prisons — they actively prevent compromised logic from persisting or escaping.

If an agent is tricked into a container escape attempt, the compromised logic cannot impact the underlying host while the agent safely iterates.

Slopsquatting: The Hallucinated Package Attack

AI Invents Packages. Attackers Publish Them.

LLMs frequently hallucinate software packages that don't exist. Malicious actors actively monitor developer forums and AI outputs for these hallucinations — then proactively publish malware under those exact fake names.

Because autonomous agents can alter dependency graphs without human confirmation, a single hallucination can pull malware directly into the build environment.

✅Source dependencies exclusively from vetted providers or internal enterprise registries
✅Enforce strict cryptographic version pinning
✅CI/CD: automatically verify SBOM entries + digital signatures (Binary Authorization)
Egress Governance

Non-Deterministic Egress Requires Non-Deterministic Controls

Traditional software: outbound traffic is predictable. Vibe-coded systems: egress is non-deterministic because it's driven by dynamically generated tools.

A simple allowlist of approved domains is insufficient. An allowlist cannot secure against indirect prompt injections hidden within third-party web pages that the agent fetches.

Restriction: Force non-interactive internet access. Agents fetch external information exclusively through offline caches or dedicated, pre-sanitised web-crawling services. All data travels through governed pathways.

Application Logic Vulnerabilities

Two Predictable Failure Patterns

❌Trusting the browser too much: AI takes the path of least resistance — dumps API keys, password validation, and session flags into client-side code. Anyone opening browser DevTools can read credentials or manipulate access level without a real password.
❌Open backends: AI connects databases and admin dashboards without enabling default-deny access controls. Row-level database security gets skipped — private user data and staging environments exposed to the public internet.
✅Shift-left advisory linters in IDE provide real-time guidance (minimal friction)
✅Deterministic CI/CD enforcement — SAST + SCA scans before production, always
Pillar 5 · Identity

Identity, Trust & High-Stakes Actions: Zero Ambient Authority

The Confused Deputy Problem

Over-Privileged Agents Get Tricked

Even with unique identity, a vibe-coded agent is susceptible to the Confused Deputy problem: prompt injection hidden inside an open-source repository (pasted into the IDE context) tricks an over-privileged agent into executing unauthorized commands on the attacker's behalf.

Because developers often use vague, highly abstracted language ("fix the backend routing"), the resulting agentic workflows are inherently broad — granting broad permissions creates an unmanageable internal threat vector.

Solution: An agent must never be the final arbiter of access. Instead of operating under the human user's delegated credentials (which grants the agent dangerous ambient access), the agent must authenticate using a dedicated, explicitly agentic identity with granular audit logs.
Zero Ambient Authority

JIT Token Downscoping

🔐SPIFFE IDs: Unique cryptographic identity for every individual agent — not shared service accounts, not the human user's credentials
🎯ABAC: Attribute-Based Access Control. Considers intent, user, time, and context of each specific action — not just the role
⏱JIT Downscoping: When agent writes a new script, the execution sandbox receives fresh, hyper-restricted credentials scoped to exactly the data sources required for that specific script. Expires the exact moment the task concludes.
📁File-tree allowlists: Read/write confined to specific project directories. Deny-by-default blocks access to secrets, build scripts, and production manifests.
MCP Spoofing & Contextual Authorization

Forged Tools Can Inject Malicious Commands

Agents increasingly rely on MCP to discover and connect to servers at runtime. A forged or compromised server can pose as a legitimate MCP tool to inject payloads or demand excessive privileges. Agents may execute malicious commands before any human intervention occurs.

Defense: Runtime LLM firewall in front of the active agent to intercept prompt injections. Centralised Agent Gateway evaluates Contextual Authorization — dynamically verifying that an agent's request to call a tool aligns with the developer's original intent. Routes all A2A invocations through a governed entry/exit point.

The "Vibe Diff" & Structured Elicitation

For High-Stakes Actions: Replace Approval Buttons

Vibe coders often can't understand complex generated syntax — simple approve/deny buttons cause confirmation fatigue, leading to blind authorization ("It Works, Ship It" fallacy).

For high-stakes actions (modifying prod databases, financial transfers, IAM changes):

🔑Cryptographic Hardware MFA: Physical touch of a USB hardware security key to cryptographically approve the execution — not just clicking "OK"
👁The Vibe Diff: Evaluator Quorum intercepts the request and translates complex generated code into a plain-English summary. Developer sees exactly how fuzzy intent maps to proposed execution steps before providing cryptographic consent
Pillar 6 · SecOps

Red / Blue / Green Security Teams: Agentic SecOps

Traditional, manual security operations cannot scale to match the velocity of vibe coding. Security operations themselves must become agentic — running in parallel with the developer's workflow continuously.

🔴
Red Team (Agent Attacker)
Injecting Adversarial Vibes
▸Proactively injects adversarial inputs — doesn't wait for external attackers to find vulnerabilities
▸Crafts sophisticated roleplay jailbreaks, buries malicious instructions inside massive blocks of RAG context that developers paste into their IDEs
▸Tests whether the enterprise agent gets distracted by poisoned context and hallucinates an insecure solution
▸Targets: invisible payloads (zero-width Unicode characters, homoglyphs in repos), repository poisoning, multi-hop attacks
🔵
Blue Team (Agent Defender)
Behavioral Analytics
▸Agent Behavioral Analytics (ABA) replaces traditional UEBA — which is ineffective for non-deterministic AI that lacks expected "normal" user behavior patterns
▸Maintains Runtime Agent Bill of Materials (AgBOM) — dynamic inventory of tools, models, and data sources the agent is actively using at any given millisecond
▸Flags deviations: agent suddenly querying unusual number of external tools, entering unbounded resource loops, confidence drift, format-compliant-but-wrong outputs
▸Drift precedes failure — catch the departure before it compounds into a crisis
🟢
Green Team (Agent Fixer)
Quarantine & Auto-Refactoring
▸When Blue detects anomaly, executes "Stateful Quarantine" via SOAR playbooks — gracefully revokes specific tool access, freezing the agent's ability to act while preserving short-term memory for forensic analysis
▸Does NOT kill the container (disruptive — leaves connected APIs in corrupted state)
▸Auto-Refactoring: autonomously rewrites insecure vibe-coded script to patch the vulnerability, presents secure alternative back to developer in the IDE — no manual formulation needed
The Triad: 3 Execution Phases
Planner Phase

When a primary agent designs a workflow, a threat-modeling skill evaluates the plan — identifies logical flaws and policy violations before the agent begins active execution.

Evaluator Phase

Evaluator Quorum reviews the proposed execution trace. Agent Defender (Blue) simultaneously verifies the AgBOM and monitors semantic context for intent drift.

Executor Phase

As Executor performs the downscoped action, Agent Fixer (Green) monitors real-world tool execution — ready to instantly quarantine or trigger auto-refactoring if a security constraint is tripped.

Pillars 6 & 7 · Observability

Observability: Auditing the Agent's Mind

You cannot secure what you cannot see. In traditional microservices, HTTP 200 OK indicates success. In an agentic system, a "success" status might mask a scenario where the agent's logic has quietly cascaded into a hallucination loop.

Tracing the "Vibe Trajectory"

From Fuzzy Intent → Compiled Code

Using OpenTelemetry, aggregate API calls, tool inputs/outputs, RAG retrievals, and token latency into a complete Vibe Trajectory. Three span types:

📦agent.session — captures entire task duration
🧠agent.think — records internal reasoning and prompting cycle prior to action
🔧agent.tool — logs specific arguments and latencies of environmental interactions

Pair traditional logging with Centralised Content Scanning that explicitly inspects all dynamic code snippets retrieved by the agent at runtime. This securely binds the agent's internal reasoning loop to its physical actions.

Denial of Wallet (DoW) Attacks

Adversaries Bankrupt You Via Infinite API Loops

Adversaries intentionally trigger infinite, computationally expensive API loops to deliberately bankrupt the organization's cloud and LLM billing accounts. Observability isn't just an uptime concern — it's a security requirement to prevent financial attacks via runaway computation.

✅Track token consumption, inference latency, and cost of self-repair loops via span attributes
✅Tail-based dynamic sampling: drop routine successes, retain traces with errors or excessive self-repair
✅Set cost-based circuit breakers that pause agent execution if hourly spend exceeds threshold
Intent Drift & Trust Decay

Trust Is a Degradable Asset

As a vibe-coded agent generates logic and pulls in new tools, its security perimeter constantly fluctuates. Static SBOMs become instantly stale.

Instead: monitor a Runtime Agent Bill of Materials (AgBOM) — a living document mapping the agent's active blast radius at any given millisecond.

Trust Decay: Trust is lost when an agent's chain of thought pursues sub-goals diverging from the original human vibe. Example: "optimize the database query" → agent drifts toward downloading an unauthorized indexing library.

Checkpoints & Circuit Breakers

Auto-Rollback When Drift Detected

1️⃣Before codebase modifications: generate a version control checkpoint (git commit)
2️⃣ABA continuously evaluates Vibe Trajectory against AgBOM — any instability penalizes the dynamic Agent Trust Score
3️⃣If Trust Score drops below threshold: automated "circuit breaker" trips — rolls back changes using the checkpoint, gracefully revokes tool access, freezes autonomous execution
4️⃣Environment preserved for forensic analysis — not destroyed, because the audit trail has value
Evaluation Framework

Why Evaluating Vibe Coding Agents is Fundamentally Different

Challenge 1: The Underspecification Gap

"There is no spec"

Traditional software testing operates on the assumption that a complete, rigid specification exists before a single line of code is evaluated. Vibe coding is the exact opposite.

"Make the dashboard load faster" is not a test case. The prompt relies entirely on the model's latent knowledge, aesthetic judgment, and domain expertise to fill in operational gaps. The first job of evaluation: determine whether the agent successfully bridged this gap and reconstructed the right unstated spec.

Challenge 2: User Can't Validate Output

Non-technical users can't review 600 lines of code

Even experienced engineers cannot review AI-generated code in real time. The gap between "the agent thinks it succeeded" and "the code is actually correct" is wider here than in any other agent category.

This is why evaluation must be systematic and automated — human review cannot be the primary quality gate when code is generated faster than humans can read it.

Challenge 3: Iterative Sessions on Live Codebase

Bad early decisions compound across turns

Each turn modifies real files. A wrong architectural decision on turn 2 poisons every subsequent turn. Evaluation has to cover not just turn-level decisions but the full arc of a multi-turn conversation on a living codebase with its own conventions, dependencies, and history.

The relevant question is not "was turn 4 correct?" but "did the user converge on something they wanted?" Sessions abandoned mid-flow are the most informative failures — far more than turn-level errors.

Security Recap: The Practical Baseline
🛡Sandbox the Vibe Loop: Always execute dynamically generated scripts within kernel-level, network-isolated sandboxes. Embed SCA to scan for hallucinated/vulnerable dependencies before production.
🛡Shift the Perimeter Left: Trusted sources + verified registries. Advisory linters in IDE. Strict deterministic checks at multiple CI/CD pipeline points.
🛡Enforce Zero Ambient Authority: Never grant a "Global Key." Mandate delegated identities + JIT hyper-restricted tokens. Replace blind approval buttons with mandatory "Vibe Diff."
🛡Deploy Agentic SecOps: Virtual Red Team for Adversarial Vibes. Agent Behavioral Analytics for AgBOM monitoring. Green Team for auto-refactoring on vulnerability detection.
Evaluation · 7 Dimensions

What to Evaluate: 7 Dimensions in 2 Groups

User-facing dimensions: what the developer experiences directly. Internal dimensions: what the agent does invisibly. Safety/Responsible AI is transversal — intersects all dimensions simultaneously.

USER-FACING DIMENSIONS
1
Intent Satisfaction
Did the agent build what the user meant, not just what they said? The hardest dimension. Intent is unstated, ambiguous, and shifts mid-session. What the user ultimately judges the agent on. Treat the first 1–2 user messages as the rubric — derive acceptance criteria automatically from the session prefix.
2
Functional Correctness
Does the code build, run, and pass tests? The floor, not the ceiling. Easy to measure but easy to game: tests can be deleted or mocked to make red turn green without fixing anything. Always validate against ground truth, not just CI green.
3
Visual & Behavioral Correctness
For agents producing web apps or UI, the artifact IS the rendered output — not the code. Code-level metrics miss the point entirely. The page either looks right and behaves right, or it doesn't. Requires browser-based testing and multimodal LLM judges.
4
Cost & Efficiency
Token spend, wall-clock latency, tool-call count, iteration count — how many corrections did the user have to issue before convergence? An agent landing the right diff in 1 turn is a different product from one needing 8 corrections.
INTERNAL DIMENSIONS
5
Code Quality & Convention Matching
Does the code match the project's idioms, patterns, and naming conventions? A diff that passes tests but violates the codebase's style is a vibe-coding failure even when locally correct. Requires knowing the project context — static linters only catch syntactic conventions.
6
Trajectory Quality
Did the agent take a sensible path — read related files first, sequence edits coherently, pick the right tool at each step? Correct output produced by bad reasoning is a fragile success. Trajectory evaluation catches 20–40% more failures than output-only scoring. (Latitude, March 2026)
7
Self-Repair Behavior
When the build fails, a test breaks, or the user says "no, not like that" — does the agent recover or compound the failure? Recovery quality compounds across a multi-turn session. An agent that recovers elegantly after the first correction is fundamentally better than one that needs 3+ tries.
Cross-cutting: Safety & Responsible AI intersects all 7 dimensions — code vulnerabilities (D2, D5), refusal behavior (D1), content safety (D1, D7), IP exposure (D5). Evaluate alongside each, not as a separate gate.
Evaluation · Methods

How to Evaluate: 6 Methods + Standardized Benchmarks

Method 1: Automated Functional Testing

Cheapest Signal Available

Run the build, test suite, and linters on agent output. Standard tooling: pytest, jest, eslint, mypy — plugged into CI. Cheapest signal available.

Best for: Dimensions 2 (correctness), 5 (code quality rule-checkable parts)

Method 2: Security & Safety Eval

Static Analysis + Adversarial Probing

SAST tools (Snyk, Semgrep) find code vulnerabilities. git-secrets catches credential leaks. Scripted red-team suites test refusal behavior. Cross-cutting — evaluates safety alongside all other dimensions.

Best for: Dimension 6 (safety/responsible AI) transversally

Method 3: LLM-as-Judge

Score Against Rubrics at Scale

A peer model scores outputs against rubrics — evaluates intent satisfaction, style, and trajectory quality. Gemini scoring against the original user prompt. Swap positions of reference and actual outputs to eliminate ordering bias. Calibrate to 90% human agreement.

Best for: Dimensions 1 (intent), 5 (quality/style), 6 (trajectory)

Method 4: Browser-Based Testing

Multi-Step Workflows Against Deployed App

Run multi-step workflows against the deployed app. Playwright scripts interacting with rendered UI. Screenshot comparison against reference states. A multimodal judge looking at rendered pages catches what code-level evaluation misses: broken mobile layouts, wrong button states, accessibility failures.

Best for: Dimension 3 (visual/behavioral correctness)

Method 5: Trajectory Inspection

Analyze Reasoning, Tool Calls, Retrievals

OpenTelemetry traces with span-level tool-call data. Trace-replay tools bind each model invocation to the actions that followed. Evaluate plan coherence, tool selection appropriateness, and repair quality.

Best for: Dimensions 6 (trajectory), 7 (self-repair)

Method 6: Online + Human Review

Live Traffic + Senior Engineer Review

Online: sample live production traffic at a biased 1% (high-cost sessions, sessions with many corrections, abandoned sessions). Human review: structured annotation by senior engineers — the only ground truth for intent satisfaction and safety nuance. Calibrates all other methods.

Best for: Calibration + Dimension 1 (intent), 5 (quality code review)

Benchmarks: Vibe Code Bench (zero-to-one web app generation), SWE-bench Verified (code changes on real repos), LiveCodeBench (contamination-resistant). Warning: A high SWE-bench score proves the agent can navigate structured Python repos — it provides zero guarantee the agent has the aesthetic judgment to vibe code a consumer-facing application.
Applied Tips

Applied Tips for Vibe-Coding Agent Evaluation

Tip 1: Use Session Prefix as Intent Rubric

The closest thing to a spec

Vibe coding has no spec to test against. The closest equivalent: the first 1–2 user messages. Treat them as the rubric — derive evaluation criteria automatically from the session prefix, then score every subsequent turn against them. The only practical way to evaluate intent satisfaction at scale.

# Derive criteria from opening turns
opening = " ".join(session.user_messages[:2])
criteria = client.models.generate_content(
  model="gemini-3-pro",
  contents=f"Produce 3-5 acceptance criteria for: {opening}"
).parsed["criteria"]
# Score every agent turn against criteria
score = client.models.generate_content(
  contents=f"Does this output satisfy {criteria}? Score 1-5"
).parsed
Tip 2: Judge the Rendered Artifact, Not the Code

The user judges the output — not the diff

A multimodal model looking at the rendered page catches problems code-level evaluation misses entirely: layout broken on mobile, contrast too low for accessibility, button states wrong. Pair multimodal judge with Playwright assertions — judge catches visual/design, assertions catch broken interactivity.

result = client.models.generate_content(
  model="gemini-3-pro",
  contents=[
    "Score layout_match, styling, interactive_correctness",
    user_spec,
    types.Part.from_bytes(data=screenshot_bytes,
                          mime_type="image/png")
  ]
)
Tip 3: Evaluate Session Convergence, Not Turn Accuracy

"Did the user converge?" not "Was turn 4 correct?"

A vibe-coding session is multi-turn by construction. Sessions that converge in few turns are success cases. Sessions abandoned mid-flow are the most informative failures — far more than individual turn errors. Cloud Trace exposes a vibe-coding session as a single trace tree.

def session_outcome(trace):
    return {
      "converged": trace.last_turn.user_signal == "satisfied",
      "turns_to_converge": trace.user_correction_count,
      "abandoned": trace.last_user_action == "close",
      "cost_to_converge": trace.total_token_cost_usd
    }
Tip 4: Mine User Corrections as Labeled Failure Data

Every "no, not like that" is gold

Every user correction is a labeled failure example — and vibe coding produces these in volume. Cluster them and systematic gaps in the agent become visible much faster than building a synthetic failure benchmark.

corrections = [t.user_message for trace in traces
               for t in trace.turns if t.is_correction]
emb = client.models.embed_content(
  model="text-embedding-005", contents=corrections)
clusters = KMeans(n_clusters=8).fit(vectors)
# clusters.labels_ = prioritized failure modes list
Observability is the prerequisite. You cannot evaluate an agent's internal reasoning without seeing it. Without complete OpenTelemetry traces, agent failures appear as inexplicable monolithic events — impossible to diagnose, impossible to fix systematically.
