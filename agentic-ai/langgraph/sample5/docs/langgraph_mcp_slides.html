Why MCP

One protocol instead of N x M glue

Before

Every app wires every tool by hand. 5 agents x 8 services = 40 custom integrations, each with its own auth and schema code.

With MCP

A service ships one MCP server. Any MCP client (LangGraph, Claude, an IDE) can use it. 5 + 8 = 13 pieces.

Analogy: USB-C for AI tools. The model does not change; how it discovers capabilities does.

One host can hold many clients, one per server. Messages are JSON-RPC 2.0 in both directions.

What a server offers

Three primitives

Tools

Model-controlled

Actions the LLM decides to call: add, get_weather, lookup_order.

Resources

App-controlled

Readable data addressed by URI: math://constants, and later skill://...

Prompts

User-controlled

Reusable templates the user picks: explain_step_by_step.

Only tools become LangChain tools automatically. Resources and prompts are read through the session (sample 1 shows it).

On the wire

The handshake

The adapter hides this, but it is just three calls.

  • initialize agree on version and capabilities
  • tools/list discover names, descriptions, JSON schemas
  • tools/call run one tool
--> {"method": "tools/list"}
<-- {"tools": [{
      "name": "multiply",
      "description": "Multiply two numbers.",
      "inputSchema": {...a, b: number}
    }]}

--> {"method": "tools/call",
     "params": {"name": "multiply",
                "arguments": {"a": 23, "b": 17}}}
<-- {"content": [{"type":"text","text":"391.0"}]}

Sample 1: server

A stdio server in 15 lines

FastMCP turns type hints and docstrings into the tool schema the model sees. The last line picks the transport.

# servers/math_server.py
mcp = FastMCP("math")

@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers."""
    return a + b

@mcp.resource("math://constants")
def constants() -> str: ...

@mcp.prompt()
def explain_step_by_step(expression: str): ...

mcp.run(transport="stdio")
Sample 1: client

Launch, discover, wrap

  • Config says how to launch the server
  • get_tools() spawns it, handshakes, wraps tools
  • client.session() gives a live connection for resources and prompts
client = MultiServerMCPClient({
  "math": {
    "transport": "stdio",
    "command": sys.executable,
    "args": [str(SERVER)],
  }
})
tools = await client.get_tools()

async with client.session("math") as s:
    await s.list_resources()
    await s.read_resource("math://constants")

app = build_app(tools)

Sample 2: HTTP

Same server code, different transport

The server is now a long-lived service at 127.0.0.1:8765/mcp. The client config has a url and no command.

# servers/weather_http_server.py
mcp = FastMCP("weather",
              host="127.0.0.1", port=8765)
...
mcp.run(transport="streamable-http")

# 02_http.py  (one client, two transports)
MultiServerMCPClient({
  "math":    {"transport": "stdio", ...},
  "weather": {"transport": "streamable_http",
              "url": "http://127.0.0.1:8765/mcp"},
})
Sample 2: run it

Two terminals make it real

# Terminal A: the service
uv run servers/weather_http_server.py

# Terminal B: the agent
uv run 02_http.py
# reusing weather server on :8765

What to notice

One question triggers get_weather (HTTP server) and multiply (stdio server) in the same turn. The agent sees one flat list of four tools and does not know which transport each uses.

Running 02 alone also works: it starts the HTTP server as a subprocess and stops it afterwards.

Sample 3: skills

Tools give capability. Skills give know-how.

Tool

lookup_order(id)

Can fetch an order. Says nothing about whether it may be refunded.

Skill

refund-policy

A procedure: look up the order, apply the 30 / 60 day rules, escalate above $500.

A skill is a folder: SKILL.md (YAML frontmatter with name and description, then instructions) plus optional references/ and scripts/. It follows the open Agent Skills format.

Skills over MCP

SEP-2640: skills are resources

Final since 2026-09-13. No new primitive: every file in a skill is an ordinary MCP resource under skill://, read with resources/read.

  • skills/list and skills/get return frontmatter plus a sha256 digest per file
  • Server declares io.modelcontextprotocol/skills
skill://refund-policy/SKILL.md
skill://refund-policy/references/
        escalation.md
skill://support-tone/SKILL.md

# listing entry (spec)
{ "uri": "skill://refund-policy/SKILL.md",
  "frontmatter": {"name": "refund-policy",
                  "description": "..."},
  "resources": [{"uri": "...",
                 "digest": "sha256:...",
                 "size": 812}] }
Progressive disclosure

Pay for context only when needed

1. Discoverlist resources, keep SKILL.md, advertise name + description only
2. Loadmodel calls load_skill, we read SKILL.md
3. Drillread_skill_file for references, only if told to
4. Actskill says which tool to call
5. Answercite the rule that decided

With hundreds of skills, step 1 keeps the prompt small. That is the whole point of the pattern.

Honest limits

What sample 3 simplifies

Not implemented
  • skills/list and skills/get: the Python SDK lacks them, so we use plain resources/list
  • Digest verification
  • User approval before activating a skill
  • Running skill scripts (needs sandboxing)
Security reminder

A skill is instructions from a server. Treat third-party skills like third-party code: it can steer the model. Digests prove consistency, not trust.

Adoption is early: at finalization no mainstream IDE or CLI harness supported the extension.

Recap

Remember this

MCP moves tool discovery out of your code. stdio launches a local server; HTTP connects to a shared one. Skills are just resources the host reads on demand, so the agent learns how, not only what.

Transport

Config only. Server code is the same.

Graph

Unchanged ReAct loop, async calls.

Skills

Discover cheap, load on demand, verify.
