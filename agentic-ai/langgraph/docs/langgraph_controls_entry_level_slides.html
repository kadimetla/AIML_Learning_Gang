LangGraph basics

Run, control, pause, dispatch, debug

Entry-level slides for understanding `invoke`, `Command`, `Send`, `interrupt`, and debug streaming.

Goal

Students should be able to look at a LangGraph example and explain which API starts the graph, which API controls it, which API fans out work, and which API pauses it.

One sentence each

The five terms

`invoke`

Run the graph once and wait for the result.

`Command`

Send a control instruction such as resume, update, or route.

`Send`

Create dynamic work for a specific node.

`interrupt`

Pause inside a node and ask for outside input.

`debug`

Observe execution details while the graph runs.

Thread

The workflow instance selected by `thread_id`.

invoke

`invoke` runs a graph

Inputstate update
Graphruns nodes
Stateupdates merge
Resultreturned to caller

For beginners: `invoke` is the first method to learn. It is the normal way to call a compiled graph when you want the final result.

invoke code

Start or continue one thread

The same graph definition can serve many users. `thread_id` tells LangGraph which conversation or workflow instance this call belongs to.

config = {
    "configurable": {
        "thread_id": "support-ticket-1"
    }
}

result = graph.invoke(
    {"question": "Can I get a refund?"},
    config=config,
)
Common confusion

`invoke` is not always “start from scratch”

New `thread_id`

LangGraph starts a new workflow state.

thread_id = "ticket-1"

Existing `thread_id`

LangGraph loads the existing checkpoint and continues from that state.

thread_id = "ticket-1"
Command

`Command` is control input

Use normal dictionaries for ordinary state input. Use `Command` when you want to control the graph.

from langgraph.types import Command

Command(
    resume={"approved": True},
    update={"notes": ["approved by manager"]},
    goto="answer_user",
)
Command cases

Three common uses of `Command`

`resume`

Continue after an `interrupt()`.

Command(resume=True)

`update`

Apply a state update while controlling the graph.

Command(update={"x": 1})

`goto`

Route to a node by name.

Command(goto="review")
interrupt

`interrupt()` pauses inside a node

It returns a value only after the graph is resumed. On the first run, it pauses the graph and sends the payload to the caller.

from langgraph.types import interrupt


def approval_node(state):
    decision = interrupt({
        "question": "Approve refund?",
        "ticket": state["question"],
    })

    return {"approved": decision["approved"]}

resume code

`Command(resume=...)` answers the pause

Use the same `thread_id`, or LangGraph will not know which paused run to continue.

result = graph.invoke(
    Command(resume={"approved": True}),
    config={
        "configurable": {
            "thread_id": "support-ticket-1"
        }
    },
)
Important rule

The interrupted node re-runs from the top

Unsafe before interrupt

def node(state):
    send_email("Please approve")
    decision = interrupt("Approve?")
    return {"approved": decision}

The email can be sent twice.

Safe before interrupt

def node(state):
    payload = {"amount": state["amount"]}
    decision = interrupt(payload)
    return {"approved": decision}

Building a payload from state is safe to repeat.

Send

`Send` creates dynamic node work

Use `Send` when the graph decides at runtime how many tasks to launch.

from langgraph.types import Send


def split_questions(state):
    return [
        Send("search", {"query": q})
        for q in state["queries"]
    ]
Send example

Fan out search work

Input3 queries
Routerreturns 3 Sends
Search nodequery A
Search nodequery B
Search nodequery C

`Send` is not for pausing. It is for dispatching work to nodes, often parallel map-style work.

Command vs Send

Both can route, but they mean different things

`Command(goto=...)`

Control the current graph path.

return Command(goto="review")

`Send(...)`

Create a task for a node with custom input.

return Send("worker", {"item": item})
debug

`debug` helps you see what happened

Debug streaming is for observation. It does not change graph behavior.

for event in graph.stream(
    {"question": "Can I get a refund?"},
    config=config,
    stream_mode="debug",
):
    print(event)
Debug use

When should students use debug?

Learning

See which node ran and when.

Troubleshooting

Find where state changed or where a graph paused.

Testing

Verify execution order and emitted events.

Exercise 1

Name the API

Ask students which API belongs in each blank.

# A. Run the graph and wait for result
result = graph._____(input, config=config)

# B. Pause inside a node
answer = _____({"question": "Approve?"})

# C. Resume after the pause
graph.invoke(_____(resume={"approved": True}), config=config)

# D. Dispatch one node per item
return [_____("worker", {"item": item}) for item in items]
Answers

A: `invoke`, B: `interrupt`, C: `Command`, D: `Send`.

Exercise 2

Find the bug

What can go wrong when this workflow resumes?

def approval_node(state):
    create_ticket("Need approval")

    decision = interrupt("Approve?")

    if decision["approved"]:
        refund_customer(state["payment_id"])

    return {"approved": True}
Expected answer

`create_ticket` is before `interrupt()`, so it may run again when the node resumes. Move it elsewhere, store a ticket ID, or make it idempotent.

Common mistakes

Beginner pitfalls

Wrong `thread_id`

Resume fails or starts the wrong workflow because the config points to another thread.

No checkpointer

Interrupt resume cannot work because there is nowhere to load paused state from.

Side effects before interrupt

Emails, tickets, or payments may happen twice.

Using `Send` to pause

`Send` dispatches work. It does not wait for human input.

Final summary

Keep this mental model

`invoke` runs. `Command` controls. `Send` dispatches. `interrupt` pauses. `debug` observes.

Runtime

Use `invoke` or `stream` to execute the graph.

Control

Use `Command` to resume, update, or route.

Workflow design

Use `Send` for dynamic work and `interrupt` for HITL.
