LangGraph HITL

How interrupts work

A student-friendly deep dive into pausing, checkpointing, resuming, and writing safe node code.

Learning goals

  • Understand what `interrupt()` does internally.
  • Explain why a checkpointer is required.
  • Resume a workflow with `Command(resume=...)`.
  • Write code that is safe to re-run.
Mental model

Interrupt means “pause and ask outside world”

Node runsnormal graph execution
interrupt()asks for input
Checkpointstate is persisted
Caller returnsworker is free
Resume latersame thread_id

Key point: LangGraph does not keep a live Python stack waiting. It saves durable state and lets the process return.

Basic code

A node can request human input

The value passed to `interrupt()` is returned to the app as the interrupt payload.

from langgraph.types import interrupt


def review_node(state):
    decision = interrupt({
        "type": "approval",
        "question": "Approve refund?",
        "amount": state["amount"],
    })

    return {"approved": decision["approved"]}
Compile

Interrupts require a checkpointer

The paused workflow must be stored somewhere durable so it can be resumed by a later request.

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START

builder = StateGraph(State)
builder.add_node("review", review_node)
builder.add_edge(START, "review")

graph = builder.compile(
    checkpointer=InMemorySaver()
)
First call

The first invoke reaches the interrupt

Use a stable `thread_id`. This is the address of the workflow instance.

config = {
    "configurable": {
        "thread_id": "refund-123"
    }
}

result = graph.invoke(
    {"amount": 100, "approved": None},
    config=config,
)

# result contains __interrupt__
Returned payload

The app receives an interrupt object

What the node requested 
interrupt({
    "question": "Approve refund?",
    "amount": 100,
})
What the caller sees 
{
  "__interrupt__": (
    Interrupt(
      value={"question": "Approve refund?", "amount": 100},
      id="..."
    ),
  )
}
Who resumes?

LangGraph waits for an external caller

Human UI

A user clicks approve, reject, edit, or answer.

Backend API

The server receives the UI action and calls the graph.

Worker/service

A queue consumer, scheduler, or external system can resume too.

The human usually does not call LangGraph directly. The app resumes the graph on behalf of the human.

Resume

Resume with the same `thread_id`

`Command(resume=...)` supplies the answer that `interrupt()` will return when the node re-runs.

from langgraph.types import Command

result = graph.invoke(
    Command(resume={"approved": True}),
    config={
        "configurable": {
            "thread_id": "refund-123"
        }
    },
)
Most important detail

The node starts over on resume

First run 
def node(state):
    print("before")
    answer = interrupt("Approve?")
    print("after")

Prints `before`, then pauses.

Resume run 
def node(state):
    print("before")
    answer = interrupt("Approve?")
    print("after")

Prints `before` again. Then `interrupt()` returns the resume value and the node continues.

Why re-run?

LangGraph saves state, not Python stack frames

This makes interruption durable and scalable. A paused run does not occupy a worker.

Saved

  • State values
  • Checkpoint metadata
  • Pending writes
  • Interrupt payloads
  • Resume metadata

Not saved

  • Live call stack
  • Open network sockets
  • Local variables outside state
  • Worker thread
  • In-progress side effects
Unsafe pattern

Do not perform one-time side effects before interrupt

def review_node(state):
    send_email(
        to="manager@example.com",
        subject="Please approve refund",
    )

    decision = interrupt("Approve refund?")
    return {"approved": decision["approved"]}

This email can be sent once before the pause and again when the node re-runs on resume.

Safe pattern

Before interrupt: compute, read, prepare

def review_node(state):
    review_payload = {
        "question": "Approve refund?",
        "amount": state["amount"],
        "customer_id": state["customer_id"],
    }

    decision = interrupt(review_payload)

    return {"approved": decision["approved"]}

This is safe because building the payload from state can be repeated.

External effects

Put irreversible actions after approval

def refund_node(state):
    decision = interrupt({
        "question": "Approve refund?",
        "amount": state["amount"],
    })

    if decision["approved"]:
        refund_customer(
            payment_id=state["payment_id"],
            amount=state["amount"],
            idempotency_key=f"{state['request_id']}:refund",
        )

    return {"refund_status": "approved"}

Even after interrupt, use idempotency keys for external APIs because retries or failures can still re-run work.

Dynamic HITL

Interrupt only when runtime logic requires it

def risk_gate(state):
    risk = score_risk(state)

    if risk > 0.8:
        decision = interrupt({
            "type": "high_risk_review",
            "risk": risk,
            "action": state["proposed_action"],
        })

        if not decision["approved"]:
            return {"status": "rejected"}

    return {"status": "approved"}
Multiple interrupts

Resume by ID when more than one is pending

Why

If several parallel tasks interrupt, one plain resume value is ambiguous.

How 
graph.invoke(
    Command(resume={
        interrupt_id_1: {"approved": True},
        interrupt_id_2: {"approved": False},
    }),
    config=config,
)

Exercise

What happens on resume?

Ask students to count how many times each line can run.

def node(state):
    log_to_database("started review")
    payload = {"amount": state["amount"]}

    decision = interrupt(payload)

    if decision["approved"]:
        refund_customer(state["payment_id"])

    return {"done": True}
Expected discussion

The database log before `interrupt()` can happen twice. The refund is after approval, but should still use idempotency.

Checklist

Interrupt-safe node design

Good before `interrupt()`

  • Read graph state
  • Compute deterministic values
  • Build a review payload
  • Decide whether HITL is needed

Avoid before `interrupt()`

  • Charging or refunding money
  • Sending emails or messages
  • Creating tickets
  • Non-idempotent external writes
Summary

What students should remember

`interrupt()` pauses by checkpointing. `Command(resume=...)` continues the same `thread_id`. The interrupted node re-runs from the top, so code before the interrupt must be safe to repeat.

Pause

Raises a special interrupt, saves state, returns payload.

Resume

External caller sends a resume value to the same thread.

Design

Keep state compact and make side effects idempotent.
