Why this matters

The problem every one of these tools is solving

"It works on my machine" is a dependency-management failure, not a mystery.

Isolation

Project A needs django==4, project B needs django==5. Installing both globally breaks one of them. You need a separate environment per project.

Reproducibility

"Works on my machine" happens when your teammate's pip install silently resolves different transitive versions than yours did last month.

Resolution

Your dependencies have dependencies. Two packages can each demand an incompatible version of a third. Something has to solve that constraint problem.

Distribution

Once your code is useful to someone else, you need a standard format to package it and a registry to publish it to — that's PyPI.

The landscape

Five names, three different jobs

PyPI

The registry. Where packages are hosted. Not a tool you run — a website/API every tool below talks to.

pip

The installer. Ships with Python. Talks to PyPI, installs into whatever environment is currently active.

conda

A parallel universe. Its own installer + environment manager + package format, not limited to Python.

poetry

Dependency manager + build tool. Wraps pip/venv concepts with a lock file, and can build & publish too.

uv

All of the above, rewritten in Rust. Installer, resolver, venv manager, lock file, build backend, publisher, even a Python-version manager.

venv (or virtualenv) is the fourth quiet character here — the standard-library mechanism for isolated environments that pip, poetry, and uv all build on top of.

PyPI

PyPI is a format before it's a website

Every tool on these slides ultimately produces (or consumes) the same two file types.

sdist — source distribution

A .tar.gz of your source tree plus metadata. Portable, but installing it may require a build step (e.g. compiling C extensions) on the user's machine.

wheel — built distribution

A pre-built .whl (a zip file) that pip can unpack straight into site-packages. No build step at install time — this is what makes pip install fast.

What actually describes a package today

pyproject.toml — a single, tool-agnostic manifest standardized across three PEPs:

  • PEP 518 — declares the [build-system], so pip knows what to install before it can even build your package
  • PEP 517 — a standard build-backend interface, so any frontend (pip, uv, poetry) can build any backend (hatchling, setuptools, poetry-core, uv_build)
  • PEP 621 — the standard [project] table: name, version, dependencies, in one format every tool reads

pip

pip — the installer everyone starts with

Ships with Python. Talks directly to PyPI. Installs into whatever environment is currently active — global, or a venv.

Strengths

  • Always available, zero setup
  • Simple mental model: one command, one index
  • Universal — every CI system and tutorial assumes it exists

Limitations

  • No lock file by default — requirements.txt is whatever you typed or froze, not a resolver-verified graph
  • Doesn't manage environments itself — pair with venv
  • Doesn't build or publish packages on its own

The two-file pattern (pip-tools)

requirements.in   # human-edited, loose
    requests>=2.31
    rich

requirements.txt  # pip-compile output, fully pinned
    requests==2.32.3
    rich==13.8.1
    urllib3==2.2.2
    ... (all transitive deps, pinned)

See sample_pip/ — both files, plus a script that only runs once they're installed.

pip — hands-on

The pip + venv workflow

# 1. create an isolated environment
python -m venv .venv
source .venv/bin/activate        # .venv\Scripts\activate on Windows

# 2. install pinned dependencies
pip install -r requirements.txt

# 3. run something that needs them
python demo.py

# 4. regenerate the pin file after editing requirements.in
pip install pip-tools
pip-compile requirements.in

# 5. snapshot exactly what's installed (not the same as a real lock file!)
pip freeze > requirements.txt

Try it: cd dependency/sample_pip and run the block above.

conda

conda — not really a Python tool

conda manages binaries, of which Python packages are only one kind. That's the whole reason it exists alongside pip rather than instead of it.

What makes it different

  • Installs compiled, non-Python dependencies — CUDA toolkits, MKL, gcc, HDF5, GDAL — that pip has no concept of
  • Own package format (.conda/.tar.bz2) and channels (conda-forge, defaults) — separate from PyPI entirely
  • Manages the Python interpreter itself as just another package
  • mamba is a drop-in, much faster reimplementation of the conda solver (conda's uv, in spirit)

environment.yml

name: dep-demo
channels:
  - conda-forge
dependencies:
  - python=3.12
  - numpy
  - pandas
  - scikit-learn
  - cudatoolkit=11.8   # not a Python package —
                          # this is the point
  - pip
  - pip:
      - rich            # layer in pip for the rest
conda env create -f environment.yml
conda activate dep-demo
conda env export --no-builds > environment.lock.yml   # reproducible pin

conda

When to reach for conda — and when not to

Reach for conda when...

Your stack needs GPU/CUDA drivers, MKL-accelerated numpy, or other compiled scientific libraries where pip wheels are missing, broken, or platform-specific. Classic in ML/data-science and HPC environments, and historically much less painful on Windows for exactly this reason.

Skip conda when...

You're building a pure-Python app or library with no native/GPU dependencies. It adds a second package universe, a slower solver, and — critically — you cannot publish a conda package to PyPI; PyPI only understands sdists and wheels.

Common real-world pattern: use conda (or an ML-vendor base image) to get the GPU/CUDA layer right, then pip install the rest of your Python dependencies inside that environment.

poetry

poetry — dependency management as a product

One tool for the whole lifecycle: resolve, lock, install, build, publish — with a deterministic solver so "it worked on my machine" stops being a coin flip.

Strengths

  • poetry.lock — every transitive dependency pinned with a hash, committed to git
  • Manages its own virtualenv per project automatically
  • Dependency groups (dev, test, ...) instead of separate requirements files
  • poetry build / poetry publish built in — no extra tools

pyproject.toml (Poetry 2.x)

[project]
name = "dep-demo"
version = "0.1.0"
dependencies = [
  "requests>=2.31",
  "rich>=13.7",
]

[tool.poetry]
packages = [
  {include = "dep_demo", from = "src"}
]

[tool.poetry.group.dev.dependencies]
pytest = "^8.0"

[build-system]
requires = ["poetry-core>=2.0.0,<3.0.0"]
build-backend = "poetry.core.masonry.api"

Poetry 2.x adopted the standard PEP 621 [project] table — earlier versions used a poetry-only [tool.poetry] schema for everything.

poetry — hands-on

The poetry workflow

# install deps + this package into an auto-managed venv, write poetry.lock
poetry install

# add a runtime dependency (updates pyproject.toml + poetry.lock)
poetry add httpx

# add a dev-only dependency
poetry add --group dev pytest

# run inside the managed venv without activating it
poetry run pytest

# build sdist + wheel
poetry build

# publish to PyPI (needs a token: poetry config pypi-token.pypi <token>)
poetry publish

Verified in sample_poetry/ — poetry check and poetry build both pass as-is.

uv

uv — one tool, written in Rust, for speed

From Astral (the Ruff team). Reimplements pip, pip-tools, venv, poetry's workflow, pyenv, and pipx as one binary — reported 10–100x faster installs and resolution because it's not Python resolving Python packages.

What it replaces

  • pip + pip-tools → uv pip, uv add
  • venv → uv venv (automatic via uv sync/uv run)
  • pyenv → uv python install 3.12
  • pipx → uv tool install
  • poetry build/publish → uv build, uv publish

pyproject.toml

[project]
name = "dep-demo"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
  "requests>=2.31",
  "rich>=13.7",
]

[dependency-groups]
dev = ["pytest>=8.0", "ruff>=0.6"]

[build-system]
requires = ["uv_build>=0.11.7,<0.12.0"]
build-backend = "uv_build"

Same [project] table PEP 621 shape as Poetry 2.x — the manifest format has converged, only the backend differs.

uv — hands-on

The uv workflow

# create .venv, install deps, write uv.lock — all in one step
uv sync

# add a runtime dependency
uv add httpx

# add a dev-only dependency
uv add --dev pytest

# run a script — auto-syncs the env first, no "activate" needed
uv run python -c "import dep_demo; print(dep_demo.hello())"

# build sdist + wheel
uv build

# publish to PyPI (needs UV_PUBLISH_TOKEN)
uv publish

Verified in sample_uv/ — uv sync, uv run, and uv build all ran clean and produced a working wheel.

Where the analogy breaks

  • No groupId. PyPI names are one flat global namespace — requests is requests for everyone. No com.company:requests disambiguation, which is why typosquatting is a bigger practical risk on PyPI than on Maven Central.
  • Resolution is stricter, not looser. Maven's classic "nearest wins" can silently pick a wrong transitive version. pip's modern resolver, poetry, and uv all resolve against one single environment (no classpath-per-jar isolation) and fail loudly on a real conflict instead of silently picking one.
  • ~/.m2 isn't quite matched. Maven's local repo doubles as "where mvn install publishes your in-progress artifact for sibling projects." Python's equivalent for that job is an editable install (pip install -e . / uv pip install -e .) or a path dependency, not the download cache.

Decision guide

Which one do you actually reach for?

Default answer in 2026: uv

For new pure-Python projects, apps, and libraries. It's faster, it does everything poetry does plus Python-version and tool management, and its manifest is the standard PEP 621 format — low lock-in if you change your mind later.

conda / mamba

When your stack has real native/GPU dependencies — CUDA-enabled PyTorch, MKL-backed numpy/scipy, geospatial libraries (GDAL). Common as the base layer in ML environments, often with pip/uv layered on top for the pure-Python packages.

poetry

Perfectly good, mature choice if a team already standardized on it — the workflow is nearly identical to uv's. Not usually worth migrating away from unless speed or Python-version management is a real pain point.

pip + venv

Still the right teaching tool for "what is actually happening under the hood" — every other tool on this slide is built on the same concepts pip and venv expose directly. Also the safe default when a environment (CI image, notebook) only guarantees stdlib + pip.

Rules that surprise people

  • Package names are global and first-come-first-served across all of PyPI
  • A given name==version can never be re-uploaded, even to fix a typo — bump the version instead
  • Use semantic versioning (MAJOR.MINOR.PATCH) so consumers' >=/^ constraints behave predictably
  • Auth is via API tokens now, not username/password — scope one token per project
  • The build backend (hatchling / setuptools / poetry-core / uv_build) is an implementation detail — the output format (sdist + wheel) is what PyPI actually cares about

Publishing — hands-on

Tool-agnostic build & publish

sample_pypi_package/ uses plain hatchling as its build backend on purpose — it proves the package isn't tied to pip, poetry, or uv. Any of them can build it.

# build (works with pip's `build`, or equally with `uv build` / `poetry build`)
python -m pip install build twine
python -m build              # -> dist/*.whl and dist/*.tar.gz

# inspect exactly what will ship
unzip -l dist/*.whl
twine check dist/*             # catches bad README rendering, missing metadata

# rehearse on TestPyPI first — same rules, mistakes are free to fix
twine upload --repository testpypi dist/*
pip install --index-url https://test.pypi.org/simple/ aiml-learning-gang-greeting-kit

# the real thing, once you're confident
twine upload dist/*

Also builds and publishable via uv build / uv publish or poetry build / poetry publish — same source tree, your choice of frontend. Verified locally: build → twine check (PASSED) → pytest (2 passed).

Takeaways

What to actually remember

  • PyPI is a format (sdist + wheel, described by pyproject.toml) before it's a website — every tool here just produces or consumes that format
  • pip + venv is the substrate everything else is built on — worth understanding even if you never use it directly day-to-day
  • conda solves a different problem (native/binary/GPU dependencies) — it's not a pip competitor, it's a superset for a specific niche
  • poetry and uv converged on the same idea: a lock file + one command per lifecycle step. uv is the faster, newer, more batteries-included version of that idea
  • Whatever you build, rehearse the publish on TestPyPI — PyPI has no undo button for a given version
